### Blocker

**1.1 The standalone Windows installer cannot install anything. No release exists.**
- What's wrong: `install-m9r.ps1` only installs from a GitHub release tagged `m9r-engine-vX.Y.Z` in `ayaanali-ai/M9R`, with assets `m9r-engine-windows-x64.zip` and `.sha256`. The release API returned `[]` today. The release workflow only runs when an `m9r-engine-v*` tag is pushed, and no such tag exists locally (`git tag -l "m9r-engine*"` is empty).
- Evidence: `scripts/install-m9r.ps1:33-36,48-56`, `.github/workflows/m9r-engine-release.yml:3-6`.
- What the user sees: "No published M9R engine release was found. The standalone installer is not publicly available yet." Nothing installs.
- Related: the `-Web` path, the `m9r-engine.exe` commands in `docs/INSTALL_EXTENSION.md:43`, the dashboard's "Connect a computer" command (1.2) and the overlay (1.19) all depend on this missing binary. `/docs/get-started` is honest about it (`page.tsx:9`).
- Smallest safe fix: push tag `m9r-engine-v0.1.0` so the existing workflow publishes. Until then, remove the installer and `m9r-engine.exe` references from `docs/INSTALL_EXTENSION.md:43`.

### High

**1.2 The dashboard's "Connect a computer to team memory" command points at a file most users don't have.**
- What's wrong: the primary command runs `%USERPROFILE%\.m9r\bin\m9r-engine.exe`. Only the standalone installer creates that file (1.1). `npm`/`npx m9r-cli setup` copies JavaScript hook files instead, because `engineSource()` only matches when the running process is itself `m9r-engine.exe`. The fallback `m9r cloud connect` only works after a global install.
- Evidence: `ConnectComputerSection.tsx:51-53,62-66`, `src/lib/native/native-commands.ts:115-118,149-167`.
- What the user sees: PowerShell "is not recognized as a name of a cmdlet". The token is shown only once (`:61`), so it is burned.
- Fix: show `npx m9r-cli cloud connect <token>` as the primary command.

**1.3 `npx m9r-cli init` fails from a normal terminal, yet the dashboard tells users to run it there. OpenCode is never auto-detected.**
- What's wrong: `cmdInit` needs `resolveAgentKind`. That function only detects Codex (`CODEX_HOME`/`CODEX_THREAD_ID`), Claude Code (`CLAUDE_CODE`/`CLAUDECODE`) and Grok (`GROK_BUILD`/`GROK_CLI`). There is no OpenCode branch.
- Evidence: `src/lib/oathlock-cli-core.ts:190-203,1123-1129`, `src/lib/agent-detection-core.ts:34-38` (PATH detection exists, but only `connect` uses it).
- What the user sees: `init failed: Could not determine agent kind. Re-run with --agent-kind <name>`. `FirstRunCard.tsx:12` says "Run this once in the folder your agent works in", and `MachineConnectionBanner.tsx:33-37` says "Run this once in the repository you control". Neither mentions running it inside the agent. `/agents` (`page.tsx:54,62`) does say so, but lists only Claude Code and Codex.
- Two related traps:
  - If `CODEX_HOME` is set globally, every shell identifies as Codex. `init --agent-kind claude-code` then fails with "Agent identity mismatch … Connect Codex from Codex" (`:194-198`).
  - `--agent-kind claude` (a natural guess) inside Claude Code gives the same mismatch error, because nothing maps `claude` to `claude-code`.
- Fix: switch every dashboard and docs surface to `npx m9r-cli connect`, which detects agents on PATH without needing to run inside one.

**1.4 After `connect`, the very next documented commands (`doctor`, `whoami`, `rules`, `disconnect`, `rotate-token`) report "no token" from a normal terminal.**
- What's wrong: `connect` saves tokens to `.m9r/agents/<kind>/local.json` (`oathlock-cli-core.ts:1291`). With no agent detected in the environment, `readLocal()`/`resolvedLocalPath()` fall back to the legacy `.m9r/local.json`, which `connect` never writes (`:258-266`). `doctor`, `whoami`, `rotate-token` and `disconnect` take no `--agent-kind` at all (`:3463-3470`).
- Evidence: `:3021-3037` (doctor: `[FAIL] .m9r/local.json exists`, then "Run: m9r-cli init"), `:3190-3193` (whoami), `:3236-3240` (disconnect: "No local M9R connection found").
- What the user sees: the Guide's step 2 (`connect`) followed by step 4 (`doctor`) fails (`marketing-content.ts:7,9`). The Guide's "Disconnect hosted access: `m9r-cli disconnect`" (`:14`) cannot revoke anything that `connect` created.
- Fix: in a normal shell, have `readLocal()` with no detected kind check `.m9r/agents/*/local.json` (one profile means use it; several means ask for `--agent-kind`), and accept `--agent-kind` on these five commands.

**1.5 "Connect your first agent" appears while agents are connected. Brief item (a): confirmed.**
- What's wrong: the card is gated on `agent.connected` (`src/app/dashboard/agents/page.tsx:312`). `connected` means a fresh heartbeat, not a registration (`src/lib/agent-workspace-data.ts:708-709,751`). "Fresh" means `last_seen_at` within 90 seconds (`src/lib/agent-presence.ts:9`, `src/lib/agent-dashboard-presenter.ts:72-77`). The card's own comment claims "Shown … only until an agent is connected, then never again" (`FirstRunCard.tsx:3-5`).
- Why it happens:
  - **(i) Nothing keeps the connection fresh after `connect`.** `last_seen_at` is only bumped by an authenticated API call (`src/lib/agent-join-service.ts:832-834`). `connect` makes one call (minting the machine credential) and then starts no heartbeat process: `runtimeTrigger` excludes `connect` (`scripts/m9r-cli.ts:2716-2717`). About 90 seconds later the card comes back.
  - **(ii) Wrong workspace or a failed query.** Connections are filtered to the dashboard's active workspace (`page.tsx:104-112,130-131`). If the claim was approved while a different workspace was active (`agent-join-service.ts:284`; neither claim page names the workspace), or if the query throws (`page.tsx:128` swallows the error), the list is empty.
- What the user sees: at the same moment, the profile menu banner says "Registered agents are offline and reconnecting … No new approval is required" (`MachineConnectionBanner.tsx:19-27`, `ProductShell.tsx:205`), and Settings > Agents lists those agents (next item).
- Fix: gate the card on `!agents.some(a => a.registered)` and let the existing offline banner cover the stale state.

**1.6 Three different definitions of "connected agents".**
- Watchfloor: the active workspace only, live within 90 seconds (above).
- Settings "Connected agents": all active rows the viewer *created*, in **every** workspace, with no liveness check (`agent-join-service.ts:707-721`). A teammate's connection appears on the Watchfloor but not in Settings, and an agent from another workspace appears in Settings but not on the Watchfloor.
- Profile menu: "No agents connected" counts live agents only (`ProductShell.tsx:200`).
- Fix: use one presenter for all three, with `registered` and `live` shown as separate states.

**1.7 The sidebar "Connect agent" action lands on a page with no connect instructions.**
- Evidence: `ProductShell.tsx:179` goes to `#agents`. That pane renders ConnectedAgentsSection, ConnectComputerSection (memory tokens) and Advanced (`SettingsView.tsx:76-84`). The only CLI text in it is `npx m9r-cli terminal runtime` under Advanced (`:123,130`).
- Fix: put the connect command block at the top of that pane.

**1.8 `init` and the routine agent commands quietly turn on the "experimental, not public" runtime and a login autostart.**
- What `init` prints: "The local terminal runtime is optional and experimental; it is not part of the public launch offer" (`oathlock-cli-core.ts:1350-1353`).
- What it does next: starts that runtime (`m9r-cli.ts:2716-2719` → `ensureRuntimeAfterAgentCommand`), then asks "Start the M9R runtime automatically at login? [Y/n]" (default yes). In a script with no TTY it installs the autostart with no prompt at all (`:2629-2631,2683-2693`).
- `rules`, `inbox` and `run start`, which `/agent.md` tells agents to run on every task, also start the runtime. On Windows they print "Note: M9R Runtime is not set to start at login. Run: m9r service install" (`:2697-2710`).
- `cli/README.md:150-171` says these commands "do not promise" a terminal and that the service "should not be presented as a production terminal feature".
- Fix: start the runtime only when `ACP_BRIDGE_ENABLED` or an explicit flag is set, and drop the Windows nag.

**1.9 `connect` registers a Windows login task without asking, and points it at the npx cache.**
- What's wrong: `ensureLocalBrokerAutostart` registers the "M9R Web Broker" scheduled task with no consent prompt. Compare `setup`, which asks separately (`native-commands.ts:294-296`). The task runs `process.argv[1]` (`m9r-cli.ts:2431-2433,2480-2494`). Under `npx` that path is inside the npx cache. The codebase already documents this exact risk for hooks: "`npx` runs it from a cache that is later cleared, which would silently kill the hooks" (`native-commands.ts:101-103`). The broker path has no equivalent copy step.
- What the user sees: after the npx cache is cleaned or the version changes, the broker silently stops starting at sign-in.
- Two more problems on the same path:
  - A second `connect` in another repo keeps the broker on the *first* repo's folder (`m9r-cli.ts:2462-2466`).
  - On macOS and Linux this step returns `ok:false` and `cmdConnect` then **exits 1 and skips machine-sync setup** (`oathlock-cli-core.ts:1494-1499`, `m9r-cli.ts:2425-2427`), even though every approval succeeded.
- Fix: ask before registering the task. Copy the CLI entry into `~/.m9r/bin` first, the same way hooks are handled. Treat "unsupported OS" as a warning and continue to machine sync.

**1.10 After `connect`, nothing installs the browser extension or explains how.**
- Evidence: the success message only says "The browser extension becomes ready after its authenticated handshake" (`m9r-cli.ts:2554`). Only `web setup` copies the extension and opens the extensions page (`docs/INSTALL_EXTENSION.md:3,25`).
- What the user sees: a user who followed the Guide (`connect`) has no extension, so browser multiplayer, the product's headline (`README.md:3`), never starts.
- Fix: end `connect` with "Next: `npx m9r-cli web setup` to add the browser extension", or offer to run it.

**1.11 `install-m9r.cmd` will be blocked on a default Windows 11 machine once a release exists.**
- What's wrong: it runs `powershell.exe -NoLogo -NoProfile -File install-m9r.ps1` with no execution-policy override, and a test enforces that (`scripts/install-m9r.cmd:5`, `scripts/install-m9r.test.mjs:108-110`). Microsoft's documented default policy on Windows client SKUs is `Restricted`, which refuses `-File` scripts. A downloaded unsigned script is also blocked under `RemoteSigned`. This is inferred from the documented policy, not run.
- Fix: before anything ships, either sign the script or use `-ExecutionPolicy Bypass -File` scoped to this one process, and update the test and the docs' "no bypass" claim together.

**1.12 @mention menu can render under the pill. Brief item (b): layering bug confirmed by z-index.**

- Fix: inside the overlay, hide the pill or move it up when the page reports an open menu, or have the overlay skip the M9R dashboard origin.
- Related lows are in 1.20.

**1.13 Reasoning-effort choices do not follow the chosen model. Brief item (c), part 1: confirmed.**

## 2. Names and identity

### High

**2.1 Watcher avatars in chat show teammates' full emails or raw user ids.**
- Evidence: the channel roster maps `userId` to `email ?? userId` (`ConversationPanel.tsx:1033-1035`) and feeds the presence avatars, their initial and their title tooltip (`:544-551`). The API sends every member's email (`src/lib/conversation-service.ts:1217-1224`). The viewer's own entry is also an email, not "You".
- Fix: use `row.name` (already computed server-side) and "You" for the viewer, and stop returning `email` from `listConversationHumanRoster`.

**2.2 The "Who can join" picker in ChannelSwitcher shows emails or user ids.**
- Evidence: `src/components/product/ChannelSwitcher.tsx:293`, `const label = member.email ?? member.userId`.
- Fix: use a name built with `personLabel()`.

**2.3 Settings > Team lists members by full email, or by raw id when there is none.**
- Evidence: `SettingsView.tsx:460`. A code comment treats this as acceptable: "teammate emails are already visible to each other in Settings -> Team" (`src/app/dashboard/agents/page.tsx:202-203`). That contradicts the standing rule.
- Fix: show the name as the primary label. If the email must stay, show it only to owners, as secondary text.

**2.4 The same person can appear under different names, and stored names go stale.**
- Four different fallback orders are in use:

## 4. Error handling and leaks

## 5. Other inconsistencies a demo could expose

### High

**5.1 No scheduled jobs run in production.**
- What's wrong: the four sweep jobs (`work-signal-sweep`, `stale-run-sweep`, `workflow-scheduler`, `idle-session-sweep`) are scheduled only in `vercel.json`. `wrangler.jsonc` has no `triggers.crons`, the only other worker config explicitly has `"crons": []` (`services/mission-worker/wrangler.jsonc`), and no Supabase `pg_cron` migration exists.
- What the user sees: runs and sessions whose agent died are never swept, so they look "running" forever. Schedule-triggered channel workflows never fire. Work-signal downgrades never happen.
- Fix: add Cloudflare cron triggers, plus a `scheduled()` handler that calls these routes with `CRON_SECRET`, or move them to `pg_cron`.

**5.2 Rate limits can be bypassed on Cloudflare.**
- Evidence: `clientAddress()` trusts `x-vercel-forwarded-for` first, then `x-forwarded-for` (`src/lib/rate-limit.ts:17-25`). On Cloudflare a client can send any `x-vercel-forwarded-for` value and it arrives untouched, so every request can get a fresh rate-limit key. That includes unauthenticated routes such as `/api/agent/register`.
- Fix: use `cf-connecting-ip`, and drop the Vercel header.

### Low

**5.3** The terminal is switched on in production (`wrangler.jsonc` `NEXT_PUBLIC_M9R_TERMINAL_ENABLED: "true"`), while the CLI and docs call it experimental and not part of the public offer (`oathlock-cli-core.ts:1351`, `src/app/agents/page.tsx:64-70`).

**5.4** On approval, a claim joins whichever workspace is active at that moment (`agent-join-service.ts:284,396`), but neither `/claim/[claimId]` nor `/claim/batch/[batchId]` shows the workspace name. This is one cause of 1.5(ii).
